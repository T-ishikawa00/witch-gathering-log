# データ・拡張・Codex引継ぎ契約 R1

## 1. ファイルの役割
`data/world_catalog.json` が今回の関係表の正本候補。Markdown・HTML・Excel・CSVは同じデータから生成した閲覧用。Excelだけを編集して実装へ渡すと同期しないため、変更はJSONへ反映して検査・再出力する。編集機能や同期ツールを納品したわけではない。

本JSONは**数値未確定の設計スキーマ**。ゲームへそのまま読み込んで稼働させる実行コンテンツではない。`null` を0に読み替える本番ローダーは禁止。

## 2. エンティティを分離する
地域／エリア／魔物／素材／入手先／装備型／レシピ／到達フラグ／キャラクターをIDで結ぶ。表示名や並び順をIDにしない。今回の `R01` 等は安定IDとして扱い、拡張で名称が変わっても再採番しない。

到達条件は `gates.requires` の依存関係が意味を持つ。`rank` は今回の一直線の本編を検査・表示するための補助値。将来の枝分かれに `rank >= 7` のような条件を横展開せず、必要フラグの集合を参照する。

装備型と装備個体、初回勝利と繰り返し戦闘、人物加入と所持素材は別のデータ。ドロップ表はアイテム説明文を解釈して作らず、明示IDを参照する。

## 3. G1からの変更記録

- G1の固定18装備・3地域・単体戦は維持保管。本書は新しいG2コンテンツ提案であり、G1 content.jsonを上書きしない。
- 4人編成、敵の狙い、回復・弱体・反撃連鎖は新参照戦闘モデルが必要。旧69,984戦の一致は本書の戦闘保証ではない。
- G1の15分/1装備・素材120・放置24hはG1の仮値。本書の50素材へ等配分などの形で流用しない。
- 6内部装備枠を共有する案と猫の表示名・適格タグは未承認のG2スキーマ提案。
- 初期2人→森の中ボス後に弟子→森の深部合流で鍛冶師という加入順は今回の提案。

## 4. 4人戦で新たに必要な契約

戦闘イベントには発生元、対象、直接攻撃／継続／反撃の区別を持たせる。反撃が反撃を呼び続けるループ、支援で起きた追撃から同じ支援が再発動するループは、別途のトリガー仕様で遮断する。

前衛／後衛の狙い、全体攻撃、死亡・復帰、回復の対象、守る対象、弱体の解除・重ね掛け、行動順が同時の処理は未設計。これは魔物の能力表から勝手に推測して実装しない。今回の敵は必要な機構を特定する設計であり、全能力の計算仕様ではない。

## 5. 拡張時に壊してはいけないこと

既存の本編5地域は閉じた進行として保つ。新地域は既存エリアの分岐から追加し、既存エンディングやレシピに新DLC素材を後付け必須にしない。

追加する魔物は、生態上の理由と素材用途を同時に設計する。色違いを作るたびに新しい素材種類を増やさず、同種は同じ基礎素材を落としてよい。特殊素材を足す場合には明確な別用途を持たせる。

能力や見た目を変更する際は `content_version` を上げる。削除IDを別アイテムへ再利用せず、旧装備・レシピ・保存構成の参照を維持するか、明示の移行表と復旧を用意する。更新前の遠征は開始時点のコンテンツ版で精算する。

特定素材の入手先を変更するなら、新しい入手先を先に用意し、既存レシピの到達性を検査する。期限付きイベント終了で本編武器を二度と作れなくしない。

## 8. Codexへ渡すときの境界

今回は設計を読む資料であって、G2の実装開始指示ではない。採用後の実装依頼では、この設計と承認済み画像を読み、4人戦の参照モデル、装備個体とセーブの移行、代表背景の制作方式、最初の経済数値を確定してから小さく統合する。

既存G1の参照フォルダ・テスト・セーブを上書きしない。新IDへの対応表を作り、テストを別名・別versionで扱う。Git操作、外部公開、対外連絡、課金・広告SDKの導入、支払はこの資料では許可しない。

**順序は、関係設計の承認→代表ビジュアル→4人戦と経済の数値契約→実際に動く小範囲。5地域の全量制作はその先。**
