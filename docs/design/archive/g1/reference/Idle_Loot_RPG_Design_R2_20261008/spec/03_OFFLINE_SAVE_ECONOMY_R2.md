# 放置・収集・保存・課金境界 R2

## 1. G1の探索レート
15分の有効探索ごとに、指定地域の6装備から1点抽選し、素材5を得る。24時間分を一回の離席の上限とする。
8時間で32抽選＋基礎素材160。固定seed12345の灰の街道サンプルでは初入手6、重複26。重複を各素材2へ自動変換して合計212。
これはプレイヤー獲得・長期バランスを予測した数値ではない。G1で装備の役割を早めに比較するための暫定レート。

### 地域と候補
灰の街道=会心6種、苔の湿原=毒6種、旧城の回廊=防御6種。各枠の候補は概ね等確率の乱数選択。
G1の固定性能装備は再取得で上位ロールにならない。実製品でランダム副効果を採用するなら、この重複ルールをそのまま流用しない。

### 制作
素材120で対象装備を一つ指定して制作。失敗なし。課金・動画不要。素材不足・倉庫満杯なら何も引かず失敗する。
G1の18装備だけで数週間遊べるとは主張しない。長期版のドロップ率・制作コストは内容量の検証後に再設計する。

参照の `initial_state()` は報酬処理用の空所持fixture。実際のG1体験モード初期化では、ゲーム概要に従って会心6点を一度だけ付与する。貸出・バランス検証用データは通常の収集履歴と混ぜない。

## 2. 閉じている間の計算
バックグラウンドで何時間も戦闘ループを動かし続ける方式は採らない。再開時に、経過時間と保存済みの探索先から成果を計算する。
精算に必要な状態：UTCミリ秒チェックポイント、地域、地域別途中経過、地域別抽選カウンター、PRNGの基準seed、所持品、素材、世代番号、直近の処理ID。
`credited=min(max(0,now-last),24h)`。15分未満の余りを次回へ繰り越す。24hを超えた時間もチェックポイントはnowまで進め、再度開いて超過分を追加受取できないようにする。

同じ総経過時間なら、細かく開いた場合とまとめて開いた場合で抽選順と基礎報酬が同じになる（24h上限に当たらない区間）。抽選seedは地域・抽選番号から派生させ、受取画面の開き直しで抽選を変えない。

探索先変更では、まず旧地域を精算。その後地域を変更。途中の数分は旧地域に残し、新地域の報酬へ付け替えない。

## 3. 時刻変更
同一プロセス内では単調増加時間の併用を実装検討。UTCで処理し、表示のタイムゾーン変更そのものでは探索時間を増減させない。
時計が戻った場合、負の報酬や装備没収にしない。`TIME_ANOMALY`として問題区間の付与をせず、状態を保全。
明示的な確認付きで「現在の時刻から再開」を可能にする。確認後の時計基準更新では報酬を出さない。

**ローカルだけで時計改変・セーブ改変を完全防止できるとはしない。** 将来もPvP・取引・現金化を前提にしない。完全な不正対策を理由に、G1で独自サーバーを導入しない。

## 4. 所持品と分解
G1の所持枠は72。以下は保護対象：ロック済み、装備中、いずれかの保存構成から参照中、同一テンプレートの最後の1点。
保護対象を含む一括分解は全体を拒否し、理由と対象を示す。無言で一部だけ実行しない。

初期の自動処理は「固定性能が完全に同じ重複品だけ素材化」。初入手は必ず保持。処理前に規則を表示し、ON/OFF可能。
画面の注目3点は表示上の優先順位で、残りを捨てる判断ではない。G1では未所持を優先し、同条件は枠順で安定ソート。

自動処理OFFで満杯になった場合、追加分はテンプレート別の保留数として保存する。消失・探索停止にしない。保留数は画面に表示し、空き枠へ取り出すか同じ規則で素材化できる仕様をCodexで実装する。
参照Pythonは保留への追加までを検証。取り出しUIとその保存の原子性はCodex側の未実装項目。
G1では固定18テンプレートなので集計保留が可能。製品の個別ロール装備に置き換えた時の容量・保全設計は再検討が必要。

## 5. 保存トランザクション
「受取アニメが出た」時点ではなく、状態が保存成功してから完了とする。
処理の順序は、入力検証→旧状態から候補生成→計算・保護の確認→世代番号付きの原子的保存→読戻し→画面へ反映。
保存失敗時は旧状態を維持し、ボタンを再試行可能にする。空の初期データを自動で上書きしない。

ローカルUI試作はIndexedDB等のトランザクション可能な保存を使い、現在と前2世代を保持する。iOS製品版の保存アダプターは別検証。localStorageへ複数キーを順番に書くだけで「原子的保存」と称しない。
チェックサムは破損検知用で、改ざん防止・暗号化とは説明しない。世代が競合したら新しい保存を読んで再評価する。

### 重複防止
精算要求に一意なrequestIdを付与。保存した処理IDを再処理しない。同時刻に新しいIDで再要求しても、チェックポイント差が0なら付与0。
同じ旧セーブを復元して報酬を複製する攻撃を完全防止できると主張しない。参照テストは単一状態系列内の重複防止。

### 中断からの復旧
保存前・保存中・完了直後の中断、容量不足、壊れた最新世代、古いschema、二画面同時操作、途中終了をテストする。本文の要求であり、Pythonの30件だけではiOSやIndexedDBの耐久性を証明していない。

## 6. 課金・広告との境界（G1未実装）
- 基礎報酬は広告を見なくても付与。
- 任意広告と恒久スキップは、同じ条件・回数枠で同じ追加報酬を受け取る案。
- 購入状態と報酬残高・プレイ進行は別データ。購入復元=進行復元ではない。
- 広告の表示完了と報酬コールバックを同一視しない。受け取ったrewardIdを重複付与しない。
- 読込失敗・拒否・中断が通常探索や通常受取を妨げない。
- 恒久スキップを購入しても、回数や進行上限を無制限にしない。
- 復元・返金・保留・中断・通信失敗は製品版の受入対象。

広告の拒否で通常利用を妨げないこと、報酬を事前明示し、完了時に約束したものを渡すことはGoogle公式方針に沿って確認する。
https://support.google.com/admob/answer/7313578?hl=en

## 7. 長期経済を決める条件
G1に課金を入れる前に、装備取得→比較→再戦が成立するかを判定する。
G2以降は無広告・任意広告・恒久スキップの3進行条件をモデル化し、コア装備到達時刻、初回突破、目標消失までの時間、1訪問の整理操作数を比較する。
スキップ購入が「嫌な待ち時間をなくす」以上の一方的性能課金になっていないかも確認。広告を増やすことでしか商品価値が説明できなければ、商品仮説を見直す。
