# 受入基準・人による確認 R2

## 判定を分ける
A=数式・状態の正しさ、B=画面が操作できること、C=人が装備変更を楽しむこと、D=実際に利用者を獲得して購入が起きること。
AだけでC/Dに合格したと報告しない。今回の参照コードはAの一部。HTMLはBの一部。

## G1必須の自動試験
1. 同一入力・seedの再現性。速度表示1倍/2倍/省略表示の結果一致。
2. ゴールデン28戦の勝敗・時刻・残HP・発動数・内訳がPython参照と一致。
3. 729構成の列挙。未知ID・枠違反を拒否。装備コスト・段階の比較条件を固定。
4. 同時刻優先順位、毒失効境界、時間切れ、死亡後反撃なし、無限連鎖なし。
5. 攻撃88→80の混成変更で対象ボスの結果が変わる例を再現。
6. 同じ精算要求／同時刻の別要求／再起動直後に二重受取しない。
7. 15分未満の端数、8時間、24時間超過、48時間、時計巻戻し、時計再設定、探索先変更。
8. ロック・装備中・保存構成・最後の一個を分解しない。
9. 倉庫満杯でも保留に残る。制作失敗で素材が減らない。
10. 保存中断、容量不足、最新世代破損、世代競合、移行失敗。初期化で逃げない。

Pythonの30件は1〜9の一部だけを検証。10とネイティブライフサイクル、1のUI速度連動はCodexで追加が必要。

## 人による最初の確認
最初は本人が体験を確認。その後は本人が選ぶジャンル経験者5〜8名程度を目安とする。協力依頼・招待をAIが勝手に送らない。
参加者がいない間はUSER_TEST_NOT_RUN。AIの採点を代用にしない。

### 誘導しない順序
- 最初の数分は「毒が有利」「防御を上げて」等の攻略を教えない。
- 一回の帰還から、何が気になったか、どの装備を替えたかを観察。
- 敗北後、結果画面を見て何を試そうとするかを観察。
- 途中で「どこまで理解したか」を尋ねる場合、正解を誘導しない。
- 終了後に「何が変わったか」「次に何を集めたいか」「やめたくなった瞬間」を聞く。
- 続きを遊ぶかは自由。開発者への好意による継続と分けて記録。

### 記録すること
参加者コード、日時、ビルドversion、端末、ジャンル経験、説明が必要だった箇所、装備変更と理由、迷った時間、再戦の自発性、翌日の自発再訪。氏名・連絡先をゲーム内ログに保存しない。

初回の少人数観察では購入率やD7継続率を推定しない。参加人数に基づく「80%だから成功」といった統計的主張もしない。

## 止める条件
- 一つの高攻撃構成しか使われず、結果を見ても変更の意味が伝わらない。
- 装備比較より整理・閉じる操作に時間がかかる。
- 帰還が新しい判断につながらず、数値だけ眺めて終わる。
- 重要な保存・保護欠陥が残る。
- 全画面・全素材の量産をしないと判断できない、と範囲を膨らませる。

この場合はゲームの全廃ではなく、該当するループを狭く直す。G1範囲内の修正では毎回Human確認を挟まない。本番制作・有償投入・公開への段階移行は別。
