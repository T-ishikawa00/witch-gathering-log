# R463 durable authority-store candidate

Status: source prepared, NOT compiled or executed. This adds an isolated, file-backed implementation of the existing R461 `PendingPurchaseOperationStoreR461` and `AuthorityObservationStoreR461` protocols. It is not wired into the app or any production purchase path and does not write a game save.

Construction requires a canonical, private `r459-sandbox-rehearsal` directory carrying the exact R459 marker and one lowercase SHA-256 account-binding namespace. The store keeps account-specific files beneath that marked root. The supplied account-binding SHA is only a namespace key, not authentication. It rejects symlinked roots/files, hard-linked files, non-owned or group/world-accessible files, changed directory identities, foreign account bindings, unknown/noncanonical/corrupt/future schemas, and files over fixed size/count limits. It uses a process-local lock plus `flock` on a private lock file for cooperating instances/processes, and a same-directory fsynced temporary file followed by atomic rename and directory fsync for writes.

Pending requests are keyed by operation UUID, validated against their canonical request fingerprint, and can be recovered with `loadPending(operationID:)` after relaunch. The store instance is pinned at construction to one account-binding SHA-256 namespace; pending loads and writes have no caller-supplied binding parameter, so they cannot switch accounts mid-instance. A different binding opens a separate namespace. Registering the same UUID with different bytes in one namespace fails. Authority observations are namespaced by the same bound account hash and use revision compare-and-save: lower revisions fail, equal revisions must be identical, and concurrent writers must match the expected prior revision. Stale temporary files from interrupted writes are removed only after acquiring the lock and validating their ownership/type; the last committed target remains authoritative.

Storage is limited to 256 pending operations (18 MiB file cap) and one small observation file (16 KiB cap). This candidate does not encrypt pending JWS bytes; it is limited to the explicitly marked local rehearsal and uses owner-only permissions. A production integration would need a separate security/privacy review and is not implied here. Tests cover cold reopen, UUID collision, account namespace mismatch, concurrent CAS across instances, corrupt/future schemas, interrupted temporary-file recovery, symlink roots, and hard-linked files. The concurrency test is in-process across store instances; cross-process exclusion is implemented with advisory `flock` but is not exercised by a subprocess test in this candidate.

All files are additive under this candidate directory. Root owns compilation, execution, and any integration decision.
